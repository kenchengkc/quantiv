# Quantiv 📈

> An earnings analytics platform for researching options-implied expected moves, comparing volatility signals, and generating machine-learning forecasts.

Quantiv is a monorepo for analyzing expected stock-price moves around earnings announcements. It combines historical earnings data, options-derived expected moves, volatility features, live market quotes, and LightGBM forecasts in a Next.js dashboard.

The primary dashboard is served from prebuilt static JSON generated by a Python data pipeline. This keeps calendar, screener, and symbol-page navigation independent of the backend. An optional FastAPI deployment on Railway provides live ML re-inference, while Upstash Redis supports live quote delivery.

> **Research and educational use only. Quantiv does not provide financial advice.**

## Architecture

Quantiv has three primary system paths:

1. A scheduled data and ML pipeline that produces static dashboard artifacts.
2. An optional backend for live ML inference.
3. A live quote pipeline backed by Upstash Redis.

```mermaid

    PROVIDERS["DoltHub · Finnhub · FMP · FRED"]
    SYNC["Sync and reconcile data"]
    FILES["CSV and Parquet artifacts"]

    DUCK[(DuckDB)]
    SCORE["LightGBM scoring"]
    BUILD["Build frontend JSON"]
    PUB["Static JSON in apps/frontend/public"]
```

### Static dashboard path

The calendar, screener, and baseline symbol data are generated by:

```text
Provider data
→ CSV and Parquet artifacts
→ DuckDB views
→ ML scoring
→ frontend JSON
→ Next.js on Vercel
```

Generated files are placed under:

```text
apps/frontend/public/
├── weeks/
├── symbols/
├── screener.json
├── ticker-names.json
└── ticker-exchanges.json
```

The frontend reads these files directly. It does not call FastAPI on every page navigation.

### Live ML path

The optional Railway backend supports live re-inference through:

```text
Vercel
→ signed HMAC proxy
→ Railway FastAPI
→ Postgres and DuckDB-backed features
→ prediction response
```

If the backend is unavailable, symbol and watchlist pages can continue displaying ML fields included in the nightly static JSON.

### Live quote path

All quote writers share the same Upstash keys:

```text
quote:{symbol}
```

The quote system has three writer paths:

1. **Railway quote worker**
   The primary scaled writer. It uses Finnhub WebSocket data for high-priority symbols and REST requests for the long tail.

2. **Vercel `refresh-prices` cron**
   A regular-hours fallback that rotates through symbols with Finnhub and uses Alpaca IEX for selected extended-hours reporters.

3. **Vercel `refresh-broad` cron**
   An off-hours broad refresh using Polygon grouped-daily data.

Client quote reads go through:

```text
/api/stocks/batch-price
```

The route reads cached quotes, applies a short in-memory cache, and records context-weighted demand in the `quote:interest` sorted set. The Railway worker consumes those rankings to prioritize active symbols.

## Frontend API routes

| Route                      | Purpose                                                          |
| -------------------------- | ---------------------------------------------------------------- |
| `/api/stocks/batch-price`  | Reads cached quotes and records quote demand                     |
| `/api/stocks/intraday`     | Returns Alpaca IEX intraday bars                                 |
| `/api/stocks/search`       | Searches supported stock and ETF metadata                        |
| `/api/watchlist/*`         | Creates, reads, updates, reorders, and deletes watchlist entries |
| `/api/ml/predict`          | Proxies one live prediction request to Railway                   |
| `/api/ml/batch-predict`    | Proxies multiple live prediction requests                        |

## Production automation

### Nightly data refresh

Workflow:

```text
.github/workflows/daily-refresh.yml
```

Default schedule:

```text
0 11 * * *
```

This corresponds to approximately 07:00 Eastern Time during daylight saving time.

The production sequence is:

```text
Pull artifacts from R2
→ synchronize DoltHub history
→ apply Finnhub and FMP overlays
→ run provider enrichments
→ validate the earnings calendar
→ push Parquet artifacts
→ build DuckDB views
→ check freshness
→ score recent observations
→ import forecasts to Postgres
→ update market-cap and popularity metadata
→ generate frontend JSON
→ commit generated JSON and earnings CSV
→ trigger Vercel deployment
```

### Weekly model training

On Sunday, the nightly workflow can run:

```text
feature_engineering_v3
→ model_trainer_v3
→ push models to R2
→ Railway model synchronization
```

### Company-profile refresh

On Saturday, the workflow performs a Finnhub company-profile and logo sweep.

### Ticker metadata refresh

Workflow:

```text
.github/workflows/refresh-ticker-names.yml
```

This runs quarterly and generates:

```text
ticker-names.json
ticker-exchanges.json
```

from SEC EDGAR metadata.

## Performance

Initial calendar and screener loads may be delayed by:

* Logo preloading
* Live batch-quote requests
* Minimum skeleton-display timing

The static screener dataset itself is relatively small, at approximately 132 KB.

Symbol pages also ship a comparatively large client bundle and may re-fetch ticker metadata on the client.

See [`docs/PERFORMANCE.md`](docs/PERFORMANCE.md) for the current audit and prioritized improvements.

## Data behavior and limitations

* The headline expected move is generally based on a straddle or IV-derived baseline unless an ML result is present.
* ML values may come from nightly static JSON or a successful live Railway prediction.
* Calendar, screener, and baseline symbol browsing use generated JSON rather than Railway.
* Live prices are cached and may be stale or unavailable when quote providers or refresh workers are not configured.
* The `Popular` filter uses weights generated by `tools/build_popular_weights.py`.
* The popularity threshold is configured in `apps/frontend/lib/popular.ts`.
* `/public/weekly.json` is a legacy fallback.
* Primary weekly data is stored under `/public/weeks/`.
* Provider datasets can disagree on announcement dates, earnings timing, EPS, or revenue estimates.
* The earnings-calendar integrity gate reduces these inconsistencies but cannot guarantee provider accuracy.
